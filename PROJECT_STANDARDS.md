# PROJECT_STANDARDS.md

These rules are mandatory for every change in this repository.

## Architecture
- CommonJS only (`require`, `module.exports`).
- Browser route -> EJS page shell -> Alpine.js `/api/*` call -> controller -> small domain service -> simple Mongoose model -> MongoDB.
- Frontend routes never query MongoDB and never server-render business records.
- Controllers handle HTTP input/output only. Business logic belongs in services.
- No repository layer, model factory, `models/index.js`, or body/content partial architecture.
- Every list endpoint is bounded and paginated. Never add an unbounded production `.find()` list.

## IDs and relationships
- MongoDB `_id` exists only as MongoDB internal storage identity.
- Every collection has exactly one named immutable application ID generated by UUID v4 with hyphens removed: exactly 32 lowercase hexadecimal characters.
- APIs, URLs and relationships use named application IDs only (`customerId`, `productId`, `supplierId`, `salesOrderId`, etc.).
- Never expose or depend on MongoDB ObjectId for a business relationship.
- Never add Mongoose `ref` relationships.
- **No `populate()` calls.**
- **No MongoDB `$lookup`.**
- **No join-style data access.**
- When one screen needs multiple domains, make explicit bounded indexed queries and combine in application code.
- Historical commercial documents use bounded snapshots in addition to stable IDs. Product/supplier/customer edits must never rewrite old order, invoice, procurement, GST or payment history.

## Money, tax and inventory
- Store money as integer paise. Never use floating point rupees for persisted commercial amounts.
- Store tax rate as integer basis points where 18% = 1800.
- Taxable value, GST components and gross totals stay separate.
- Purchase GST and sales GST are separate domains.
- Do not infer legal ITC eligibility. Record operational ITC status only.
- Every inventory mutation creates an inventory movement record.
- Multi-record finance/inventory state changes use MongoDB transactions.
- Payment status is independent from order, procurement and delivery status.
- Payments are immutable transaction records with allocations; partial payments and advances are first-class.

## Security and operations
- OTP authentication is server-side through the configured Findoly OTP service.
- Protected pages and APIs enforce authorization.
- Secrets are environment/secret-store values only; never commit secrets.
- Sensitive mutations must be auditable.
- S3 uploads use short-lived presigned URLs and approved B2B prefixes.
- Validate all server-side input even if the UI also validates it.
- Preserve request IDs, safe error responses, health/readiness endpoints and graceful shutdown.

## UI
- Preserve Findoly's existing internal CRM visual language: Bootstrap-based compact cards, tables, forms, calm colors and responsive layout.
- Customer surfaces stay mobile-first and simple.
- Do not add a new design system or unrelated visual refactor.

## Scope discipline
- Do not add Communication Center, lead marketplace, service-provider logic, provider credits, lead unlocks or service subscriptions.
- Do not add PDF invoice generation in this app. Future PDF generation will be an external Lambda integration.
- Do not add a delivery-agent website here.
- Do not refactor unrelated working code.

## QA
- Every business rule change requires tests.
- QA scans must fail when `populate()`, `$lookup`, Mongoose `ref`, ObjectId relationship fields, or prohibited scope is introduced.
- Run `npm run qa:production` before release.

- GST classification must be explicit on sales orders before invoice issue. Never silently assume CGST/SGST or IGST.
